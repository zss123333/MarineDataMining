# 高冲突共享资源调度实验

## 问题与预先固定的设计

本实验是通用核心的可执行机制验证，不是Flatland、真实LLM或外部benchmark。复用核心，单独实现离散共享资源任务适配器，以精确判断每次承诺是否冲突。没有根据输赢选择种子或删除失败。

固定6/10个Agent、每Agent12项连续工序、每项占用一个共享资源2至4步；资源数分别为2/3。前一工序完成才能开始后一项。种子17、29、43，运行320步。独立方法、单响应、多响应、带约束反馈的多响应共24局。所有方法共享任务、初始状态、候选时刻和执行器。各Agent自行选择自己的时间，不由发起方生成私有计划。

每次提案包含发起方当前工序，队友自行提供保持或不同开工时间的响应。核心组合公开占用窗，只允许资源不重叠的组合。多响应每方最多3项，最多128次组合检查/候选；反馈方法最多3轮，在找不到组合时将已有公开占用条件送回各方，重新产生自己的响应。有限窗口为未来24步，每步执行后观察；仅承诺当前工序，不提前决定整个流程。

独立方法也使用相同时间候选，但不协商；执行器发现同资源同时占用时，本步所有冲突者都不取得进展并记录冲突。已开始的工序不能任意移走，未开始的预约可调整。该执行规则保护资源互斥，不是物理碰撞模型。所有方法适用相同规则。

指标：完成工序数/总数、全部任务完成Agent数、冲突参与步、累计等待步、消息条数与序列化字节、组合检查、准备中止、约束反馈轮数、实际提交、墙钟。复杂性是否真的发生，由冲突、协商和中止数据验证，不以Agent数代替证据。工序数按Agent与工序相关，不将其当作独立统计样本。

这是有意强耦合的压力测试，不能据它宣称普遍优势。单响应与多响应预算不同，因此同时报告开销；完整法还多了反馈预算，需将其效果解释为机制与预算的共同结果，不能声称纯架构归因。先运行固定全表，结果不佳也照录；后续改动必须新建版本。

## 运行

```powershell
& 最终作业/expr/003-flatland-core/.venv/Scripts/python.exe 最终作业/expr/005-high-conflict/run.py
```

生成任务清单统一写入`../datasets/high-conflict-v1`，本目录runs保存原始汇总和过程审计。首次运行固化清单，后续校验一致，任务不依方法变化。
