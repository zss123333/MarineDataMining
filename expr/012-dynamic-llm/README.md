# 动态变更后的真实LLM连锁协调

预先固定种子1046、1047、1048，由种子生成资源释放时刻。每配置3名相关成员和1名无关成员，比较按依赖扩组与全组重新协调。两者使用同一模型、任务合法域、冲突反馈、优先级和提交规则。

每次先协商预约，然后在实际执行前关闭原预约窗口：合法时间统一后移12单位，发起方紧急撤销旧安排，再由相关成员重新生成响应、扩组、核验版本并安装局部补丁，最后按新预约执行。模型均为真实Qwen2.5-1.5B，无规则替代。

这检验执行前反馈变化引发的修复，不是执行中抢占，也不是铁路改道或新增任务测试。依赖由任务插件显式报告，并未接入Ledger未来承诺记录；不能声称所有最新模块同时获得验证。全组法是受控对照，不是成熟事件触发SOTA。种子只变化释放时刻，三个配置不等于复杂环境泛化。

每批启动前写入manifest和源码快照，每次配置保存结果与原始模型调用。历史失败不覆盖。记录阶段有效性、完成数、输入输出token、撤销通知、扩组轨迹、无关片段保持及无关成员是否收到消息。

首批运行暴露适配器缺少`coordination_peers`时紧急撤销保守通知全组的问题，首批仍完整保留。修正后的按依赖方法只向相关成员发撤销；全组对照保持原范围。新增测试核验整个过程中无关成员不收到消息。最终批次还须运行`audit.py 批次目录`，逐项检查两次提交、撤销、连锁扩组、执行互斥与片段保持；配对轨迹是否一致单独记录，不默认相同。
