# 同构LLM Agent共享资源协调

本实验直接调用`核心源码/agent.py`和`核心源码/llm.py`。每位成员用Qwen2.5-1.5B产生自己的时间槽响应；冲突时接收公开反馈，再调用模型修订。发起方不为别人生成私有方案。协议程序检查资源互斥和版本，分别安装局部补丁。

## 设计

- 两个配置：3人、释放时刻0；4人、释放时刻2。共享资源容量1，每份任务执行1时间单位。
- 两种方法：保留有效安排的按需协调；固定轮换机会重新协调的周期对照。
- 两者使用相同模型、温度0、提示、合法输出空间、提交协议和轮换规则。每组观察2N+1轮，再按最终预约执行。
- 每次响应均真实调用模型，无缓存、调用次数上限回退或规则替代。JSON Schema限制输出格式和单人合法时间槽；约束由任务环境提供。模型在合法域内选择，不是自由语言规划，也不是自动学到约束。
- 跨人冲突由组合检查发现，通过公布较低编号成员的当前选择形成下一轮约束；优先级反馈是显式设计的协调规则，不是模型自主发明。
- 为避免未冲突成员也同时换槽，原选择仍合法时，合法输出域固定为该选择；原选择冲突时模型才重新选合法槽。这是程序施加的稳定约束，不能归因于大模型自主学会保留承诺。
- 固定轮换对照每轮检查，但只有0号成员有变更任务，轮到0号时才重新协调；不称“每步都调用模型”。

## 指标与证据

记录任务完成数、资源冲突、最终安排、执行轨迹、等待代价、模型调用、输入/输出token、调用耗时、消息字节、局部补丁和无关片段保持。全部请求与原始输出写入批次，不以成功筛选结果。运行错误写入error文件，已有部分结果保留。按需法与周期法若最终安排不同，应同时报告完成情况与等待代价，不能声称等轨迹降本。

资源任务是构造的小规模诊断，不是Flatland在线LLM对照。旧铁路数据仍是原规则版本，不能被此次接入追溯性替换。

## 运行

本机Ollama须已安装`qwen2.5:1.5b`。无需第三方Python库。

```powershell
python 最终作业/expr/011-llm-coordination/run.py
python -m unittest discover -s 最终作业/expr/011-llm-coordination -v
```

每次创建新批次。源码快照在启动时写入，模型调用过程持续保存。早期格式校验失败的批次保留用于诊断，不能把错误批次的耗时或未保存调用伪称完整统计。
