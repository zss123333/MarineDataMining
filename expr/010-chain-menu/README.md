# 连锁依赖与响应菜单诊断

## 当前流程已修正

单响应同样支持约束反馈和重新选等待时段，不再将首轮冲突作为最终失败。三种链长的单/双响应共6次均已重新运行并成功确认。旧结果保留作历史，下面旧“单响应未提交”不再支持当前方法对比。结果新增coordination_steps和total_wait_cost，不能预设多响应一定更优。硬约束先检查，只在可行组合内比较损失；预算耗尽后保留后续修订，不冒称找到全局最优。

固定3、4、5名相关成员的链，各增加一名无关成员，单响应与双响应共6次。成员首先都提出共享资源槽0；双响应还提供自己的唯一备选槽。每名成员的响应引出下一名相关方，核心扩组后重新确认。使用实际Agent状态机和局部补丁，不使用LLM或Flatland。

结果：单响应三种长度均未提交；双响应三种长度均提交互不冲突的组合。无关片段内容和版本保持不变，无关成员不被联系。此为刻意构造、可精确判定的能力诊断，验证替代选项和连锁扩组的作用，不代表复杂任务总体成功率或真实环境性能。双响应提供更多候选，不能解释为同预算纯算法领先；长度5最多32种组合，未检验大规模组合爆炸。

场景常量就在run.py中，无外部数据集，不下载或复制数据。运行输出含完整状态机轨迹、源码快照及结果。初始主选项冲突不是现实分布的采样，因此报告单独列为功能性对照，不混入009铁路36局。
