# 实验工作区说明

本目录用于落实[方案设计](../方案设计.md)。**一个独立实验一个目录，所有数据集统一存放在本目录的 `datasets/`，不得在各实验内重复下载或复制数据集。** 当前实验001已完成本机环境冒烟验收，尚无LLM协作方法有效性结果。

## 1. 目录结构

```text
expr/
├── README.md                  实验总索引与统一规范
├── datasets/                  所有实验共用的数据集根目录
│   ├── README.md              数据组织、版本和登记规范
│   └── <dataset_name>/
│       └── <version>/
│           ├── README.md      来源、许可证、版本、构建方式
│           ├── manifest.json  文件清单与校验信息
│           ├── raw/           原始数据，只读保留
│           ├── processed/     可复用的预处理数据
│           └── splits/        冻结的开发集、测试集、任务与种子清单
└── <实验编号>-<实验名称>/
    ├── README.md              实验问题、执行方法与结果入口
    ├── configs/               方法、模型、预算和环境配置
    ├── src/                   本实验代码
    ├── scripts/               运行、检查和汇总脚本
    ├── tests/                 有需要时放测试，不强制创建空目录
    └── runs/
        └── <run_id>/
            ├── config.resolved.json  实际生效配置
            ├── run_manifest.json     运行溯源记录
            ├── logs/                 程序日志、错误与重试
            ├── trajectories/         Agent动作、消息与环境反馈
            ├── metrics/              逐任务与汇总指标
            ├── figures/              本次运行生成的图
            └── report.md             结论、失败与局限
```

上图是创建实验时遵循的结构，不表示这些实验或文件已经存在。按需建立目录，不先堆放空实验。

## 2. 什么算“一个实验”

- 围绕一个明确研究问题、共享一套评测协议的工作放在一个实验目录。
- 同一实验中的方法、基线、消融、模型、种子和重复运行，用配置与 `runs/` 区分，不分别散建顶层目录。
- 研究问题或评测协议发生实质变化时建立新实验；小修正保留在同实验并记录版本。
- 目录采用三位编号加简短名称，例如 `001-environment-smoke-test`；编号保持稳定，不因排序需要反复改名。

## 3. 每个实验 README 必须说明

1. **问题与假设**：验证什么、什么结果会否定假设。
2. **范围与状态**：计划/调试/运行中/完成/失败/废弃；开始日期和变更记录。
3. **数据引用**：指向统一 `datasets/<name>/<version>/`，给出 split、任务、种子与校验信息。
4. **对照与参数**：方法、基线、消融、模型准确版本、预算、扰动和重复次数。
5. **执行方法**：依赖环境、工作目录、可直接运行的命令，以及必要环境变量名称；不写密钥。
6. **判定与统计**：主要指标、失败处理、配对方式、置信区间和成本计算口径。
7. **结果入口**：具体 `run_id`、指标文件、图和报告链接；没有运行时明确写“暂无结果”。
8. **复现限制**：缺失数据、API随机性、版本差异和已知问题。

未实际实现的命令不能伪装成已经验证的运行命令。

## 4. 数据集统一管理：必须遵守

- 数据下载、导出、合成和可复用预处理结果，都进入 `expr/datasets/`；不放实验的 `data/`、`assets/` 或其他临时目录。
- Overcooked 地图、任务实例、扰动事件序列、冻结的种子清单若作为评测输入，也统一登记在数据集版本中。交互环境没有传统静态数据集，并不意味着可以省略输入版本管理。
- 实验配置通过工作区根路径定位数据，避免依赖当前命令行目录；不要写个人电脑的绝对路径。
- 原始数据不覆盖；处理规则或测试划分发生改变时生成新版本，并记录生成脚本和输入版本。
- 开发集用于调参，冻结测试集用于最终评估；测试轨迹不能悄悄回流经验库。
- 日志和轨迹是本次运行产物，留在 `runs/`。若之后作为其他实验的训练/评测输入，明确整理成新的数据集版本，记录来源运行，不静默跨实验读取。

详细规则见[数据集说明](datasets/README.md)。

## 5. 运行与结果留存

- `run_id` 建议为 `YYYYMMDD-HHMMSS-方法名-短标识`，避免覆盖；所有方法结果必须可追溯到实际配置。
- `run_manifest.json` 至少记录：开始/结束时间和时区、运行状态、代码提交及未提交修改、环境依赖版本、模型ID、数据版本与哈希、任务/种子、命令、配置位置和错误摘要。
- 记录输入/输出/缓存 token、调用失败与重试、消息和时延；失败轨迹同样保留，不能只存成功结果。
- 派生图表和指标放本次 `run` 下，不散落在实验根或 `expr/` 根。不同运行不共写一个可变的结果文件。
- 方法调试、API失败和正式运行分开标注；没有实际结果不生成虚假数值表。
- 优先保留结构化决策摘要和可观察事件，不要求保存模型不可见的内部思维过程。

## 6. 仓库、隐私与依赖

- 不提交 API key、令牌、账号、真实用户隐私或带凭证的请求日志；分享前检查配置与轨迹。
- 数据集、大型缓存、虚拟环境、模型权重、第三方仓库副本不能未经检查直接加入 Git。公开前按大小、许可与复现需求配置忽略规则或外部存储；当前文档没有自动忽略任何文件。
- 可公开小规模配置、生成脚本、样例和必要结果；不便提交的数据提供来源、版本、校验及重建步骤。
- 环境代码属于依赖，不是数据集；若后续需要共享执行器或工具，再建立单一公共实现并补文档，避免每个实验复制后分叉。
- 不把第三方下载文件当成本项目原创，不把环境冒烟测试当作方法有效性结果。

## 7. 每次新增实验的检查清单

- [ ] 一个明确问题对应一个编号目录，README 状态真实。
- [ ] 所有输入数据引用统一 `datasets/`，无重复数据副本。
- [ ] 基线和本方法使用一致的环境、观察与执行接口。
- [ ] 配置、随机种子、模型版本和成本口径已记录。
- [ ] 结果进入独立 `runs/<run_id>/`，包含失败日志。
- [ ] 图表可追溯到原始指标，结论不超过证据。
- [ ] 更新本说明中的实验索引，无密钥与隐私泄漏。
