# 统一工具接入现有Agent插件的LLM闭环实验

## 动态依赖与外部框架对照

dynamic.py使用4名成员：collect→analyse→publish，另有独立reference。执行到逻辑时刻2时新增verify，并把publish依赖从analyse改为analyse和verify；事件发生时collect和reference已在执行。两个耗时配置、三种方法各一次。local使用现有Agent协议、就绪事件触发和局部参与；global使用同一Agent协议但周期全员重议；autogen实际调用Microsoft官方autogen-agentchat==0.7.5的RoundRobinGroupChat、AssistantAgent，每个决策轮4名成员各发言一次，并从结构化结果安装本人方案。

外部实现来源：https://github.com/microsoft/autogen ，官方文档：https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html 。这是官方轮换团队组件在本工具任务上的适配，不是AutoGen论文原始任务复现，也不是SOTA基线。未修改第三方框架代码。每个决策时刻新建团队，仅提供当前共享状态；此重置策略是本实验适配选择，未测试持久历史或更强Selector团队，不能称AutoGen最强配置。

正式批次dynamic_runs/20261118-172010：三方法共用Qwen2.5-1.5B、OpenAI兼容接口、温度0、max_tokens256、同一任务合法域与工具。六局全部完成；两配置分别14、18轮，三方法提交/完成轨迹相同，发布均在analyse与verify实际完成之后。local总调用24次，global45次，AutoGen36次；输入token分别4268、8763、8398。local比AutoGen调用少33.33%、输入少49.18%；比global调用少46.67%。无关成员3的方案版本local始终为1，global和AutoGen分别增至4、5；这说明无关计划未被重新安装，不代表任务工作被对照实际重做。

protocol_messages仅统计我们协议的Mailbox消息，AutoGen的0表示不经过该Mailbox，不是零通信，不能横向比较这一列。提示和历史因框架而异，token成本可以报告但不能归因为单一算法因素。每配置仅一次，固定能力、合法动作域多数为单选，依赖与参与者集合由任务适配器明确计算；不能宣称模型自主发现依赖。当前支持的是在此新增前置条件场景中，局部协调维持相同合法执行并减少协调调用，不支持更高完成率、复杂撤销修复或普遍优于外部框架。

预试批次171515使用了不同传输预算，不与正式结果合并；171811暴露共享异步客户端事件循环错误，已修复并保留失败记录。正式日志dynamic-shared.log有第三方Pydantic序列化警告，模型调用均返回并完成任务。audit_dynamic.py核对新增依赖、无关方案版本和逐步执行轨迹，manifest及源码快照保留运行配置。

## 首组真实LLM配对对照

compare.py在同一工具底座上增加audit和appendix两个独立工作，共6项工作；成员0和2各有两个初始就绪选项，模型不再全部单选。三个配置编号改变各工具耗时，analyse统一增加3轮延迟，执行前并不向模型透露完成时刻。这里是运行耗时扰动，不是执行中撤销承诺，也没有重新分配所有者。两方法均接收同一全局完成反馈，按需触发依据同一公开状态检测就绪工作；触发器由程序实现，不是LLM学到的能力。

对照仅改变needs_revision：周期法在轮换发起机会重议，事件法仅在空闲成员有就绪工作时重议。两方法发起机会都受现有三成员轮换限制；事件法不是立即抢占执行。每次仍全员响应，因此本组不检验局部扩组。所有者、合法域、工具、模型与完成校验相同，单次运行内部无规则回退。

comparisons/20261118-170208的6局全部完成。逐组总轮数均为13、14、15，提交与完成轨迹逐步相同。事件法调用44次，对照60次，减少26.67%；消息165对225，减少26.67%；输入token9874对13554，减少27.15%；输出443对600，减少26.17%。audit_comparison.py重新读取原始结果生成审计。失败批次不与这组结果混用。

这是内部触发消融，结论仅为：所测三种耗时配置下，保持相同工具执行效果，按需触发减少重复协调。配置编号不是多次随机采样，温度为0，每配置每法仅一次，不作显著性声明；不能证明分工优化、动态承诺修复或优于成熟外部框架。外部基线尚未落实，不将本对照称为论文原始方法。下一阶段仍需多能力分工、执行中承诺变化、相关方局部响应及可运行外部方法对比，才能回答更广义协调效果。

run.py复用现有Agent、Mailbox、run_round、OllamaDecisionModel，并继承011的ResourceTask，仅替换任务上下文、响应及执行动作。每名成员的真实模型响应经PlanPatch、协议准备与提交安装后，task.act生成ToolCall；运行器统一推进一次逻辑时间，完成产物进入下一轮observe。没有规则替代模型回答。

这不是继续扩展数字调度题，而是工具接口集成测试。任务是collect→analyse→publish，另有可独立完成的reference；三个成员能力固定。工具只返回输入任务清单，模拟耗时2轮，不模拟取蛋或设备操作。不主张这是已有公开任务、原始外部基线或真实数据分析。

运行：使用014隔离环境执行run.py；单测执行unittest discover -s本目录。源码、插件父类、调用和轨迹在runs保存。实际模型Qwen2.5-1.5B，由原有客户端调用本机Ollama。

保留失败：164302批次模型反复wait，12轮无完成任务；164538批次增加非空闲工作约束后仍wait，三次校验失败，未规则回退。164628批次由执行层根据能力、前驱完成和忙闲状态提供合法动作域；有就绪工作时排除无理由等待。8轮完成全部4项工作：首轮collect与reference并行，随后analyse，最后publish。

重要限制：最终任务所有者固定，合法动作域基本为单元素，依赖判断和不空转约束由程序提供，不能声称LLM自主学会协调；没有方法对照、动态承诺变化或统计重复。它验证真实模型→现有协调协议→工具执行→真实回执的工程链路，不验证我们的协调机制优于外部方法。后续协调实验需要非平凡的分工选择、承诺变更与共同执行底座上的公平对照。
