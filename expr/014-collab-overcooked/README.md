# Collab-Overcooked官方任务与原始基线接入

## 固定初始职责修订实验

2026-11-19新增--fixed-roles模式：厨师负责接收、锅/烤箱加工与交付，助手负责取料、按真实配方预处理与台面交接。研究仅包含初始化之后的协作，不研究角色分配。fixed_roles.py通过独立适配覆盖原解析入口，统一空格、参数引号、counter编号及已知动作别名，严格检查技能白名单/参数数量/wait范围。非法动作仍拒绝，原环境继续检查权限、手持状态与工具前置条件；不硬编码成功，也不自动代替成员完成任务。

原实现已有手持物、设备及台面提示，不能说此前完全没有观测。修订增加每轮环境序列化快照、本人状态、动作队列与固定职责，作为模型真实输入；interface-events.jsonl保存快照与解析映射/拒绝原因。完整环境可见性是新增信息条件，不能与旧原始基线公平归因于单一协调因素。此模式属于任务适配修订，不是原论文配置复现。

动作接口3项单测覆盖全部声明动作的格式、别名及非法输入拒绝，不等于所有技能均已在环境成功执行；完整执行能力以实际回合结果为准。实验7B、120步、200次调用上限，日志fixed-roles-200.log，启动批次20261119-092313-154079。结果未出前不宣称修复成功。

运行官方LLMPair入口，Qwen2.5-7B、boiled_egg、官方默认120步，单次请求超时180秒、总接口预算40次（chat与embedding均计入）。保留原始提示、动作解析、角色权限、校验与控制器，不启用旧提示修补。预算中断必须记作未完成，不能算正常完成120步。日志为`llm-acceptance.log`，逐次请求及模型原始输出仍在runs。接口超时放宽是运行参数变化，不是协调算法改动。

验收分两关：首先须由环境正奖励和完成订单记录确认原始LLM方法完成任务；然后才核对执行接口能否与协调层分离、供所有方法一致复用。前一关成功不自动等于共享执行底座已验收。当前LLMPair把角色规划、通信和技能选择耦合在一起，不能直接将其整体称为已分离的执行器。launcher的summary分别记录task_completion_observed和shared_executor_validated，后者在独立接口验收前保持false。

研究对象是协调机制，不是任务动作修补。已停用`--local-execution`，传入时明确报错；旧模块及失败日志仅作历史审计。默认原始LLMPair路径仍可运行。后文可选修订说明是历史记录，不再作为当前实验入口。

新增`execution_gate.py --source <固定源码目录>`直接复用上游RecipePolicy、Session和环境，不增加任何烹饪规则。结果与逐步日志位于`gate_runs/20261118-152433`：4种订单、双方角色共8局全部20分，分别11、17、26、43步完成。仅确认环境及脚本路径，不把RecipePolicy当作LLM执行底座，更不作协调方法排名。结果明确将LLM验收和协调比较标为未通过；这两个字段是保守的人工证据状态，不是自动推断的统计检验。

执行层必须统一技能、权限、前置条件和实际反馈；协调层仅改变分工、依赖请求、交接确认、重协调范围和时机。未来任何共享执行适配应对所有方法一致，保留原始基线与修订版身份；不能给本方法独加提示或配方，再把收益归因于协调机制。

## 可选修订：本人工作优先自行执行

`launch.py --local-execution`启用修订提示：模型根据角色空间、手持物、真实状态、成功历史和队友指令决定本人直接执行还是请求。助手可以规划并执行厨师已明确分配的工作，不再因为没有完整配方而只问不做。只有越出本人能力、缺少必要信息或确实依赖队友时请求，不能把请求当成完成证据。原始权限、物理状态和动作校验器仍然生效；提示不是强制正确性的保证。

此外只对plan字段做分号两侧空白和尾部分号清理，避免原始精确动作字符串匹配拒绝前导空格；不自动解包request，不硬编码配方，不自动把越权动作分给队友。`calls.json`同时保存模型原始response和规范化effective_response。

此模式是明确标记的修订实现，不是原始基线；不加开关仍走原始路径。每次运行保存修订代码快照和适配声明。`test_local_execution.py`的4项测试覆盖消息不原地修改、无system消息的兼容、只清理plan空白及不改请求语义。

更正此前诊断：上游支持`deliver_soup()`，不能把它本身称为不存在的动作；带前导空格的精确匹配失败与动作本身非法应分开判断。

修订首次实跑`runs/20261118-112040-779280`：1.5B、3步、22次chat和6次embedding，3次接口报错；入口正常结束，但仍为0分、无有效动作。模型仍生成嵌套request，并在锅为空时提出cook，被原校验器拦截。因此只能确认提示接入和空白规范化工作，不能宣称行为问题已经修复。日志在`local-execution-smoke.log`；下一步需要基于原始环境状态的执行归属校验与拒绝后重规划，不能仅依赖提示遵循。

## 原始基线与兼容适配

运行上游`src/main.py`，原始`LLMPair/LLMPair`，`new_env`、`boiled_egg`、默认recent_k和K=0。不是浏览器配方策略替代，也不是我们重写的群聊框架。

launch.py仅在SDK层将chat转到本机Ollama，并记录完整请求/返回；模型是Qwen2.5-1.5B，不是论文商业模型复现。上游本地模型分支用model_dirname+model，别名qwen-local避免Windows目录名冒号，发送时映射回实际模型。Python须使用UTF8模式，以兼容上游未声明编码的文本读取。

上游重复对话检测需要embedding。改用本机all-minilm替代text-embedding-3-small，保留原相似度计算与0.9阈值。该变化可能影响对话结束，必须披露，不能称严格原配置复现。不读取或使用上游密钥内容，只在客户端覆盖为本地占位值；不要把密钥文件复制到实验日志。

环境安装在本目录独立.venv，未覆盖001/003环境。采用Python3.11.15、numpy1.26.4、gym0.26.2、openai1.54.3、httpx0.27.2和transformers4.57.6；未安装未使用的训练/评测依赖。上游官方推荐Python3.8，此处属于兼容运行。

## 运行

先下载固定ZIP并解压，安装上游修改过的`lib/overcooked_ai`，不能用标准pip版overcooked_ai替代。

```powershell
$env:PYTHONUTF8='1'
$env:PYTHONIOENCODING='utf-8'
& 最终作业/expr/014-collab-overcooked/.venv/Scripts/python.exe 最终作业/expr/014-collab-overcooked/launch.py --source <固定源码根目录> --horizon 3
```

manifest保存原始入口与策略文件hash、实际模型和适配范围；calls.json保存真实chat及embedding请求。原始main直接保存每步状态、角色技能行为及得分。call-limit为防止上游无限纠错而设的安全中断，触发时不能算成功跑完。
