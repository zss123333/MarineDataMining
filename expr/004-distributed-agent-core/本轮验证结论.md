## 2. Qwen实验与公平性

`runs/qwen-holdout-pair.json`保留一场景两局：相同模型qwen2.5:1.5b、温度0、每局最多6次真实调用，之后规则回退。独立到达3/7，完整方法7/7；惩罚完成时间958与800。输入token2331与2486，输出均42；规则回退92与2669次。墙钟29.975与25.012秒，单次计时不代表稳定加速。

这与该场景的规则结果相同，不能证明LLM带来增益。框架改变候选过滤、调用时机和轨迹，因此两局不是严格同输入的框架开关消融。

另有`runs/qwen-matched-probe.json`，将同三份局部候选、相同上下文、相同调用次数分别输入模型。这只检查局部选择一致性；开关标签没有改变运行中的协调，不能当成端到端框架开关实验。原待办的严格同信息、同调用规则完整对照仍未解决，不虚假勾选。

## 3. 失败诊断

`runs/failure-replay.json`按已有动作重放Level_6/8，到达倒数第二帧时位置与日志一致。

- Level_8末段，成员2与5、2与6在当前重新生成的候选中均没有兼容候选对。至少说明继续组合这些候选无法解决当前冲突，需要更早避让或更丰富的候选；不能只靠增加确认消息。
- Level_6末段各对之间均能找到兼容候选，但两两兼容不等于全体存在共同解，也不保证能在剩余时间完成。尚不能归因于某个唯一环节。
- 重放未恢复各Agent原私有计划，因此这是固定状态候选诊断，不是原协议逐事件重演。完整失败因果诊断仍未完成。

保留集过程审计记录撤销到再安装等待、短期再次修复与参与范围。恢复代理不等于恢复正常行驶；频繁修复不等于不必要修改，后者需要反事实比较。

## 4. 当前结论

本轮完成了保留测试、直接消融、成本、不确定性和失败候选追踪，但没有达到todo原先“稳定优于有竞争力对照且成本可接受”的成功标准。不能靠把待办全部打勾来改变这个事实。

若继续研究，应优先针对进入不可恢复拥堵之前的候选生成和协调时机改进；此次保留集随后只能作开发诊断，改方法后需另设新保留集。课程报告可以如实呈现局部改善、完整模块无额外收益和开销问题，不必强行写成全面成功。
