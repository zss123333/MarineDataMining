# Flatland任务适配与闭环验证

2026-11-10。已将真实Flatland环境接入统一`核心源码/agent.py`，不再由003的集中式Coordinator决定各列车方案。当前为单进程消息模拟的分布式决策，不冒充真实网络部署或LLM实验。

## 已实现

- `src/flatland_task.py`：每个列车实例只依据自身列车状态和公开候选生成本地路线/等待响应，私有路线留在自己的Response中。
- 提案方公布候选占用与期限；其他列车自行生成可行应对及增量代价。提案方检查公开响应之间的占用和换位冲突，不读取其他适配器的私有计划。
- 选中响应经统一核心prepare/ready/commit后各自安装。保持方案可用时纳入候选，增量代价按自身剩余行程及等待计算。
- 承诺采用8步条件有效期，预测32步；每步执行一个低层动作。条件偏离或原生故障触发撤销和修复通知；这里尚未实现自适应期限选择。
- `src/run_flatland.py`：加载统一数据、实例化7个同构Agent、同步消息阶段、推进环境、保存源码快照/消息/动作/指标。调度器不选择列车路线。

适配器虽然持有Flatland环境引用，但算法只读取自身`env.agents[handle]`与公开轨道拓扑，不读取其他列车的私有计划；这不是进程级访问隔离。

## 范围与剩余工作

现在已完成“真实环境—同构Agent—候选响应—确认—执行—反馈”的运行闭环，不是正式方法有效性证据。真实模型选择、强基线与配对消融尚需另跑。

本次七列车共同完成一个交通协调任务，因此都在同一个任务组；并非按编号随意拆组来降低消息。跨组能力已有协议测试，但Flatland适配器`coordination_peers`当前为空，尚未建立真实交通任务分组与跨组资源依赖。不宣称本结果验证了跨组节省通信。

每个响应方目前为每个提案候选返回一个本地最低成本响应；若各方响应彼此冲突，提案方拒绝该组合，不会搜索响应的笛卡尔积。因此局部可行响应可能存在但未被找到，不是完备联合优化。代价目前仅为行程和等待，不含通信或修复成本项。

当前规则后端不调用Qwen；不把能运行的Task适配器冒充完整LLM元认知能力。准备到提交仍依赖同步状态冻结前提，无无死锁保证。此前“Flatland尚未接入”的描述为历史状态，以本报告为准。
