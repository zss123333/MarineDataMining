## 005 · 助手 · 2026-11-16T03:42:13.868Z

因为两个字典保存的**值的用途不同**：

- **`base_versions: dict[str, int]`** 保存“片段名 → 版本号”。版本号是整数，用来检查生成补丁后，相关片段有没有被别人修改。
- **`updates: dict[str, Any]`** 保存“片段名 → 新内容”。内容可能是列表、字典或其他计划对象，所以用 `Any`，不限定类型。

例如：
```python
base_versions = {
    "运输任务": 3,
    "准备任务": 2,
}

updates = {
    "运输任务": {"路线": ["A", "B"], "出发时间": 10},
}
```

含义是：生成补丁时，读取了第 3 版运输任务和第 2 版准备任务；应用补丁前，要确认**两者版本都没变**，但实际只更新运输任务。

所以，**`int` 是记录“第几版”，`Any` 是保存“改成什么内容”**。这里的类型注解用于表达约定，并不会自动执行运行时类型检查。

### 1. `base_versions: dict[str, int]`

**语法含义：**这是一个字典，键是字符串，值是整数。

**保存什么：**键是任务片段的名称，值是**生成补丁时，该片段的版本号**。不是执行时间，也不是任务编号。

```python
base_versions = {
    "准备任务": 2,
    "交付任务": 5,
}
```

表示生成这次修改方案时，依据的是第 2 版准备任务和第 5 版交付任务。

**程序怎么用：**`SegmentedPlan.valid()` 会逐个比较这些版本和当前版本。假如准备任务已经变成第 3 版，即使补丁只修改交付任务，也不能直接应用，因为生成交付方案时依赖的准备条件可能已经改变。

**为什么这样设计：**防止“依据旧条件生成的方案，在条件变化后仍然被执行”。因此要记录所有影响可行性的读取片段，而不只是准备修改的片段。

**对应报告：**`最终作业/最终报告LaTeX/report-content.tex:120`，方法设计与实现中的“局部变更与连锁协调”：

> 本地计划按任务片段保存。补丁记录读取过的相关片段版本，以及确实需要写入的内容。安装前先检查读取版本；通过后只更新写集合并递增对应版本，无关片段保持不变。

其中，`base_versions` 对应的是**“读取过的相关片段版本”**；使用它做校验，对应的是**“安装前先检查读取版本”**。

### 2. `updates: dict[str, Any]`

**语法含义：**同样是字典，键是字符串，但值允许采用不同类型。

**保存什么：**键是确实需要修改的片段名称，值是该片段的新内容。例如：

```python
updates = {
    "交付任务": {
        "交付时间": 15,
        "接收成员": "C",
    },
}
```

这里的新内容是字典；其他任务可能用动作列表或专门的计划对象表示，因此核心使用 `Any`，不固定具体结构。**`Any` 不表示可以随便乱填，内容仍须满足具体任务插件的约定。**

**程序怎么用：**`SegmentedPlan.apply()` 在版本校验通过后，只遍历 `updates` 中的片段，将它们替换为新内容，并递增对应版本。没有列入 `updates` 的片段不会被这个补丁覆盖。

**为什么这样设计：**一次局部调整不应该把整个计划都替换掉。上面的例子读取了准备任务和交付任务，但只更新交付任务，准备任务仍然保留。

**对应报告：**同样是 `最终作业/最终报告LaTeX/report-content.tex:120`：

> ……以及确实需要写入的内容。……通过后只更新写集合并递增对应版本，无关片段保持不变。

`updates` 对应**“确实需要写入的内容”**和**“写集合”**。这个机制还支撑报告在 `最终作业/最终报告LaTeX/report-content.tex:70` 中的表述：

> 一个小任务的变更不重做成员的全部任务。生成响应时记录相关片段版本，确认时重新核验，只修改受影响片段；未受影响的任务和已有成果继续保留。

**所以，这两行不是单纯的类型选择：`base_versions` 负责记录校验依据，`updates` 负责限定修改范围，共同实现报告所说的“版本化局部补丁”。**

**2. “独立规划”的含义**

这里指一种**不与队友协商的对照方法**：每辆列车自行生成本人的路线、等待等候选方案，按自己的代价选一个，直接更新本地计划，不经过队友响应、跨成员组合检查和共同确认。

例如，两车都觉得先进入共享区段对自己最划算，独立规划不会交换配合方案；协调方法则让双方分别提出方案，再检查能否共同执行。

## 061 · 助手 · 2026-11-18T01:29:21.063Z

**要评估，就要先把“实验程序是否正确”“模型能否完成任务”“协调机制是否有效”这三件事分开。** 当前我们把它们混在了一起，导致失败后不知道该归因于哪一层。

我建议按下面顺序做，而不是继续在同一个失败实例上反复跑。

### 1. 先验收实验程序，不比较优劣

给四种方法接入可控的测试模型，分别返回：
- 合法方案：应能被接收并完成执行。
- 资源冲突方案：应被发现，并把准确反馈送回模型。
- 修正后的方案：应能从失败恢复到成功。
- 格式错误、超时、预算耗尽：应完整保存候选及失败原因。

目前我们只验证了部分合法路径，**还没有完整验证四种方法的“发现冲突→反馈→修复→执行”链路**。这一层必须先补齐，不能用真实模型调用代替软件测试。

### 2. 用能力预检选任务难度，不急着排名

固定模型，先测试单成员能否正确完成两工序任务，再逐步增加资源竞争、跨成员依赖和动态变化。

目标是找到一个有区分度的难度区间：
- 所有方法都失败：无法比较成功后的质量与成本，应先定位共同瓶颈。
- 所有方法都轻易成功：可以比较成本，但不足以说明复杂协调能力。
- 有成功也有失败：才适合观察协调对完成率的作用。

**难度选择只用开发集；确定后冻结配置，再在未参与调试的实例上比较。** 不能看到结果不好就改任务，直到我们的方法获胜。

### 3. 正式回答两个不同问题

| 比较 | 要回答的问题 |
|---|---|
| 我们的方法 vs 已有 LLM 协调方法，如 AutoGen 的明确配置 | 相同任务与资源条件下，我们是否更有效？ |
| 我们完整方法 vs 去掉局部修复、按需触发等模块 | 改善究竟来自哪个机制？ |

无通信 LLM 和集中式 LLM可以保留，但分别属于基础参照和不同架构参照；**不能把它们全部称为外部论文算法**。AutoGen也只能按实际运行配置命名，不能代表整个框架的最佳能力。

### 4. 在同一任务上同时看“完成、质量、成本”

建议主指标按以下层次报告：

1. **任务成功率**：是否完成全部必要步骤且满足约束。
2. **动态恢复率**：条件变化后，是否能修复安排并继续完成。
3. **任务质量**：完成时间、延误或任务本身的目标值。
4. **协调成本**：输入输出 token、模型调用、消息量和墙钟时间。

失败必须计入成功率；成功样本上的成本单列，不能用“提前失败所以调用少”证明降本。最好再给出**不同调用或 token 预算下的成功率曲线**，而不是只比较某一个预算点。

### 5. 让任务真正对应我们的特点

**自建资源调度任务适合做机制诊断，不应独自承担“高复杂任务协调”的证据。** 正式实验应再接入一个已有的多步协作任务集，要求有：
- 多成员之间不可绕过的分工或交接；
- 可验证的前置依赖及执行结果；
- 中途变化后需要重新配合；
- 模型实际生成决策，而不是程序预先算好答案让模型选。

我们之前筛过的 **Collab-Overcooked 可以作为待验证候选**，但必须先核实其能力限制、动作接口和现有基线是否真的可运行，不能先认定它适合。

**所以，眼下最应该做的是：补齐四种方法的冲突恢复测试 → 做分级能力预检 → 冻结任务、提示和预算 → 在保留实例上正式配对比较。** 这才能把结果解释为协调机制的差异，而不是实验接口或模型基础能力的差异。

当前订单是 `boiled_egg`，地图把两名智能体隔开：
- **Assistant（助手）**能访问食材机、盘子机、砧板和搅拌机。
- **Chef（厨师）**能访问锅、烤箱和出餐位置。
- 双方需要借助公共台面交接食材。

因此，合理的协作过程应该是：**助手取鸡蛋并放到公共台面 → 厨师接过鸡蛋 → 放进锅里煮熟 → 取出并交付。**

仅靠厨师自己去取原料，或助手自己去用锅，都不能完成。

### 2. 助手把“自己做”错误写成了“请求别人做”

厨师首先告诉助手：

> Assistant, please pick up the egg from the ingredient dispenser and place it on the counter.

即“请从食材机取鸡蛋，放到台面上”。这个分工本身是合理的。

但助手生成的实际计划是：

```text
Assistant plan:
request('pickup(egg, ingredient_dispenser)');
request('place_obj_on_counter()')
```

这里的问题在于：**取鸡蛋、放台面原本都是助手自己应该执行的动作，它却全部包进了 `request(...)`。**

原始解析器不是“收到请求就自动替另一个人执行”的任务分配系统。它在提取当前角色的执行动作时，会跳过包含 `request`、`accept`、`deny`、`clarify` 的片段。

结果就是：

```text
助手生成两个request
→ 解析器跳过两个片段
→ 没有留下本人执行动作
→ 回退为wait(1)
→ 助手原地等待
```

所以，**日志里虽然出现了“取鸡蛋”这几个字，但环境里根本没有发生取鸡蛋。**

这里也纠正一下之前容易误解的说法：`request` 本身不是凭空编造的非法词；原始提示允许用它表示请求。错误在于**模型把请求机制用错了角色和场景**。

### 3. 厨师把“已经提出请求”误认为“对方已经做完”

随后，厨师的分析里出现了：

> Since the assistant has already been instructed to do this and is waiting, it means the egg should now be on the counter.

意思是：

> 既然已经通知助手，而且助手正在等待，那么鸡蛋应该已经在台面上了。

**这个推断不成立。**当时真实状态仍然显示：
- 双方都没有拿东西。
- 台面上没有东西。
- 成功动作历史为空。

也就是说，模型把“我让他去做了”当成了“他已经做完了”。这是**对真实执行状态的误判**，不是环境真的完成了交接。

### 4. 厨师又尝试执行自己没有权限的动作

接着，厨师生成：

```text
Chef plan:
pickup(egg, ingredient_dispenser);
place_obj_on_counter();
cook(pot0);
[NOTHING]
```

第一步就要求厨师从食材机取鸡蛋，但食材机在助手一侧。

原始校验器明确返回：

```text
Chef can not directly access dispenser.
Chef can gain ingredients with the help of assistant.
```

即：

> 厨师不能直接访问食材机，必须通过助手取得食材。

因此，这一步不是“走过去失败”，而是**动作在执行前就被权限校验拦下了**。

### 5. 收到纠错后，模型仍然没有恢复出可执行流程

厨师收到错误说明后，确实在文字分析里承认“必须让助手取鸡蛋”，但新计划是：

```text
request('pickup(egg, ingredient_dispenser)');
cook(pot0);
wait(3);
pickup(egg, pot0);
deliver_soup();
```

这仍有明显问题：
- 请求助手取鸡蛋，不代表鸡蛋已经送到锅里。
- 缺少可确认的台面交接和入锅过程。
- 使用了本次原始动作协议无法正常执行的 `deliver_soup()`。

所以，**“分析文字承认错误”并不等于“纠正后的动作序列已经合法”**。

### 结论：目前到底证明了什么？

这次3步测试暴露的是三层问题：

| 层面 | 真实表现 |
|---|---|
| 动作协议使用 | 把自己的执行动作全部写成请求，最终变成等待 |
| 状态理解 | 把“请求已发出”误判为“食材已交接” |
| 权限与流程规划 | 越权取食材，或跳过交接、入锅等必要步骤 |

**因此，目前还没有进入能够公平比较“哪种协调框架更好”的阶段：最基础的合法动作与真实状态闭环都没有建立起来。**

但也不能据此断言“全是模型能力不足、代码没有问题”。原始解析器对格式的处理、本地模型的上下文窗口与提示兼容性，都还需要单独核查；这次只是3步入口测试，不能代替完整任务评测。

|---|---|
| 属于本人，当前可执行 | 直接执行 |
| 属于本人，但前置条件不满足 | 保留本人负责，补齐前置动作或等待 |

| 双方都无法完成或动作不存在 | 拒绝计划，要求重规划 |

- 取原料是助手能做的。
- 助手当前空手。
- 鸡蛋是合法原料。

设置有限次数的纠错；连续失败就明确记录失败，避免无限对话、无限等待。

|---|---|

- 总完成时间、依赖阻塞时间。

### ReAct到底是什么？

ReAct首先是**一篇研究论文提出的方法**，不是某个软件框架的名称：

- 论文：*ReAct: Synergizing Reasoning and Acting in Language Models*
- 作者：Shunyu Yao等。
- 发表于 **ICLR 2023**，预印本于2022年公开。
- 论文：https://arxiv.org/abs/2210.03629
- 官方代码：https://github.com/ysymyth/ReAct

它把语言模型的推理与环境操作交替组织起来：

> 推理（Thought）→ 行动（Action）→ 观察（Observation）→ 继续推理与行动。

**需要纠正一个容易误解的地方：ReAct不是规定“只能想一步”。** 它的推理可以包含多步计划；只是它本身没有强制规定，每次行动前必须显式比较多步未来方案。

### 你的优化应该怎样定位？

不是简单地说“ReAct只想一步，我们想多步”，而是：

> **在ReAct的推理—行动循环中，加入显式的有限前瞻：提出若干未来行动方案，比较它们的后续结果和依赖，只执行近期动作，再根据真实观察更新计划。**

两者的区别可以这样理解：

| 方法 | 执行下一步前做什么 |
|---|---|
| 原始ReAct | 根据任务、历史和观察进行推理，选择下一动作；可以自行形成计划 |
| 我们的改进 | 明确生成未来若干步计划，检查前置条件、未来影响和风险，再选择近期动作 |
| 加入多Agent后 | 进一步检查未来计划依赖谁、会影响谁，必要时协调，而非每步都全员商量 |

例如，当前动作看起来可行，但它会占用下一阶段队友必需的资源；我们的前瞻机制应该提前识别，而不是等冲突发生才处理。

### 现在应该回到什么实验？

**主要对照必须回到ReAct，而不能只有AutoGen和全员协调。**

在同一模型、同一工具、同一任务与观测条件下，比较：

1. **ReAct基线**：正常的推理—行动—观察循环。
2. **显式多步前瞻ReAct**：加入未来计划与更新机制。
3. **多Agent前瞻协调**：在第2项基础上，考虑跨成员未来依赖。

这样才能分别回答：
- 多考虑未来几步，是否真的改善任务结果？
- 收益来自前瞻规划，还是仅仅增加了模型调用？
- 多Agent协调在前瞻基础上又带来了什么？

## 215 · 助手 · 2026-11-19T02:40:29.502Z

对，**确实有区别。上一轮我把重点收缩成单智能体规划，偏离了你要研究的多智能体协调。** 单智能体实验最多是辅助验证，不能代替我们的主实验。

关键区别不是“有没有多想几步”，而是**未来计划涉及谁，以及计划之间如何相互影响**：

| 维度 | 单智能体 ReAct | 我们要研究的机制 |
|---|---|---|
| 思考对象 | 自己接下来如何行动，也可以考虑多步 | 自己的多步计划，以及对其他 Agent 的未来依赖 |
| 计划关联 | 根据工具或环境反馈调整行动 | 将一个 Agent 的交付与另一个 Agent 的后续行动关联 |
| 变化处理 | 调整自身行动 | 识别受影响的其他 Agent，协商并更新关联计划 |
| 协调内容 | ReAct 本身不规定跨 Agent 协调协议 | 谁交付什么、何时需要、依赖是否成立、变化如何传播 |

例如，B 需要 A 的分析结果才能写结论，C 又需要 B 的结论才能完成检查。我们希望 Agent **提前看到这条依赖链**：A 发现无法按原计划交付时，及时通知 B；B 判断是否先做其他工作，并更新对 C 的交付承诺，而不是等 B、C 都执行到阻塞点才处理。

不过，表述上要严谨：**ReAct 是推理—行动范式，不局限于单智能体，也可以被放进多智能体系统中。** 因此我们的对照不应只是“单 Agent ReAct”，而应该是：

- **多 Agent ReAct 基线**：角色固定，允许正常通信，各自根据观测和消息决策，但不增加我们的显式跨 Agent 未来计划维护机制。
- **我们的方法**：在相同条件下，增加多步计划、跨 Agent 依赖与交付承诺，以及变化后的关联计划修正。
- **消融对照**：只增加各自的多步计划、不关联彼此计划，检验收益究竟来自“各自多想”，还是“面向未来依赖进行协调”。

所以，准确的研究定位应是：**在 ReAct 式多智能体执行框架之上，引入面向未来任务依赖的多步规划与协调机制。** 后续筛选开源项目也应优先找**已有多智能体协作任务、真实通信和可运行基线**的项目；AgentBoard 的单智能体 PDDL 不再作为主实验首选。
